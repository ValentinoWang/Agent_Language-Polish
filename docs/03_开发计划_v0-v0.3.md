# StyleOS 开发与验证计划 v0 → v0.3-ready（修订执行版）

> 本文是执行事实源。它综合了方案审计与实践讨论，修正了旧版的状态矛盾、过度承诺、评测口径和阶段混轴问题。
>
> **核心口径**：代码可完成的工程范围在本轮推进至 100%；只能由真实用户、真实语料和时间产生的证据，必须保持 pending，绝不通过伪造样本或轨迹“补齐”。

## 1. 旧计划的十项修订

### 1.1 状态由单轴改成三轴

旧版 `status: usable` 同时混合“Prompt 存在”“示例齐备”“盲测通过”“服务上线”等不同事实，导致 manifest 自相矛盾。现在每个 Pack 分开记录：

```yaml
delivery:
  prompt: ready
  skill: buildable
  cli: ready
  mcp: ready
  api: ready
validation:
  example: passed
  automated_smoke: passed
  formal_blind_test: pending
  real_pilot: pending
maturity: engine_compiled
```

成熟度依次为：`planned → prompt_ready → pilot_validated → engine_compiled → service_ready → optimization_ready → production_validated`。当前六个 Pack 为 `engine_compiled`，不是 `production_validated`。

### 1.2 W1-0：机器 Schema 只有一个事实源

`src/styleos/models.py` 中的 Pydantic v2 模型是机器契约唯一事实源；`styleos schema-export` 单向生成 JSON Schema。`schemas/*.yaml` 降为带解释的人工阅读示例，不与代码争夺权威。

### 1.3 内容账本分成硬锁与语义锁

- **硬锁**：成功抽取进账本的实体、数字、单位、日期、引用、公式、引语和标识符；回归必须确定性通过。
- **语义锁**：主张强度、限制条件、因果方向和商业陈述级别；使用语义比较与人工复核。

“100%”只用于**已经正确进入账本的硬锁回归**，不再偷换成“所有语义判断在真实分布上 100% 正确”。无法判断的语义项返回 `review_required`，不得自动 pass。

### 1.4 规则双投影改成分级执行

规则仍只有一个 SSOT，但每条规则声明：

```yaml
detector:
  level: deterministic | statistical | semantic | human
  type: literal | regex | counter | parser | llm_judge | manual
  blocking: true | false
```

“双投影”现在表示“同一规则同时生成写作指令和审计策略”，不再意味着所有规则都必须写成正则。

### 1.5 评测按 Pack 定义

六个 evaluator profile 分别覆盖：

- `global.deai`：硬锁、语义锁、自然度和信息密度；
- `distill`：证据准确率、跨次稳定性、跨作者区分度、事实污染；
- `imitate`：卡片批准、风格一致性和事实回归；
- `self_media`：时长误差、朗读流畅、钩子兑现、凭空经历；
- `academic`：LaTeX、引用、数字、主张强度与章节功能；
- `business`：陈述定级、事实/假设/预测分离和数字回归。

### 1.6 小样本只叫冒烟评测

- `<30`：smoke，只证明接线和明显回归；
- `30–99`：phase evaluation，必须报告样本量和置信区间；
- `≥100`：formal holdout，或采用预注册的领域适当设计。

所有正式输出采用盲名、随机顺序，并按作者或原始文档分组切分，防止同源泄漏。系统提供 Wilson 区间，不再只报一个偏好百分比。

### 1.7 真实垂直闭环是主线，而不是收尾附件

```text
授权语料
→ CanonicalDocument
→ StyleCard draft
→ 人工批准
→ ContentLedger
→ 改写/创作
→ 硬锁与语义锁审计
→ final + diff + audit
→ accept/reject/edited
→ Preference Memory + Trace
```

仓库用合成语料完成自动化接线。真实作者 Pilot 必须在获得授权语料后执行，不能用合成 fixture 冒充。

### 1.8 Trace 从第一条运行开始，Langfuse 只是适配器

核心定义 `TraceSink`：本地 JSONL 默认启用，内容默认不上传；邮箱、手机号和密钥自动脱敏。Langfuse 是可选适配器，不再作为 v0.3 内部才开始的工作项，也不默认记录私密全文。

### 1.9 图检索从文风优化主线拆出

GraphRAG/HippoRAG 属于 Evidence Memory 路线，只有真实多跳需求达到数量、普通检索失败率达到阈值时才允许启动。它不阻塞 StyleCard、改写、反馈或 DSPy 路线。

### 1.10 泛化指标改成审查触发器

- 新赛道修改核心层时，必须提交 ADR、迁移方案和全量回归；
- 共享规则比例偏低时触发架构审查，但不机械阻止合理的专业赛道上线；
- 新赛道真实成本必须包含 Pack、领域规范、示例、测试夹具、评测集和人工评审标准。

## 4. 安全与失败策略

1. 硬锁缺失或出现新增硬事实：`fail`；
2. 主张、因果和边界无法可靠判断：`review_required`；
3. 高风险学术或商业文本存在语义不确定：不得自动发布；
4. 原始语料默认只在本地存储，不进入 Git；
5. Trace 默认不捕获全文；显式开启时先脱敏；
6. StyleCard 未人工批准时，正式 imitate 任务应拒绝或明确降级；
7. 外部模型调用必须显式配置 provider、当前模型名和密钥；离线模式是默认值。

## 6. 正式 v0.3.0 的数据门槛

以下条件全部满足，方可从 `0.3.0rc1` 升级到正式 `v0.3.0`：

1. 成对反馈总数 ≥300；
2. 每个进入优化的 Pack 有足够样本；
3. 单一作者或来源占比 ≤50%；
4. 每个进入优化的 Pack 正式盲测题 ≥30，另有不参与优化的保留集；
5. Trace 覆盖至少 30 个自然日；
6. 优化前后报告样本量、置信区间和硬约束回归；
7. 硬约束不得回退；
8. 自动规则提升继续经过人工批准。

`styleos readiness` 会计算这些条件；不满足时返回非零退出码并阻止 `dspy_optimise` 与自动规则提升。

## 7. DSPy、图检索与微调

- **DSPy**：接口已留出，但只能在第 6 节门槛通过后优化 Prompt 措辞和组块顺序，不得改变内容锁、规则语义和审计门线。
- **Evidence Graph**：只有真实需求案例 ≥20、普通检索失败率 ≥20%，且确有多跳问题时才启动。
- **轻量微调**：只有成对样本 ≥2000、DSPy 收益进入平台期、保留集无回退时才进入离线评估。

## 8. 下一次真实实践

选择一位拥有明确授权的作者：准备同一渠道、同一人设的 3–10 篇近期最终稿；蒸馏 draft StyleCard；人工逐条批准；使用同一张卡完成 self_media 与 imitate 各一项真实任务；保存接受、拒绝和手改 diff；将同一 Pilot 连续用于 CLI、API、MCP 和后续优化验收。

完成后，相关 Pack 可由 `engine_compiled` 升为 `pilot_validated`。只有正式盲测和长期轨迹通过后，才继续升级成熟度。
