# StyleOS 方案总览 v2 —— 交付形态决策与落地结构

> 本文档回答一个此前悬而未决的问题：**每个写作模块做到最后，交付出去的"即插即用物"应该是什么形态——纯 Prompt 模板？用例？MCP 工具？还是别的？**
> 并把答案直接做成了本仓库的目录结构。原始完整方案（架构、四类记忆、蒸馏流程、评测体系等）归档于 [`01_StyleOS_原始方案.md`](01_StyleOS_原始方案.md)，其技术判断本版全部沿用，本文只写**修订与新增**。
> openclaw-media 已有能力的盘点与复用策略见 [`02_openclaw_media_复用清单.md`](02_openclaw_media_复用清单.md)。

---

## 0. 今天就能用（急用入口）

不用等任何基础设施，[`packs/`](../packs/) 下四个模板现在就是成品：

| 你要做的事 | 复制这个文件 |
| --- | --- |
| 手头有篇 AI 味稿子，改成人味、事实不动 | `packs/global/prompt.deai_rewrite.zh.md` |
| 把某博主的语料蒸成风格卡（StyleCard） | `packs/distill/prompt.style_distill.zh.md` |
| 用指定风格写/改一篇东西 | `packs/imitate/prompt.style_imitate.zh.md` |
| 从选题写一条可开拍的口播脚本 | `packs/self_media/prompt.script_writing.zh.md` |

串联用法：先 `distill` 蒸卡（人工批准）→ 再 `imitate` 或 `self_media` 带卡写作；不需要贴人时直接 `global.deai`。

## 1. 核心结论：交付形态不是单选题

### 1.1 四种候选形态的真实差异

| 形态 | 是什么 | 依赖 | 强项 | 致命弱项 |
| --- | --- | --- | --- | --- |
| **Prompt Pack** | 单文件模板，复制进任意对话框 | 零 | 立刻能用；任何模型通用；人可读、可人工审 | 锁定项靠模型自觉，无程序化校验；长语料装不下 |
| **Skill / 斜杠命令** | Claude Code 技能包，进 git | Claude Code | 多终端一条命令调用；版本随 git 同步；可挂脚本做硬校验 | 绑定 Claude Code 生态 |
| **CLI** | `styleos rewrite draft.md --profile …` | uv 装一次 | 程序化账本抽取/回归、统计特征、批量处理、产物落盘 | 需要装环境，非技术协作者用不了 |
| **MCP 工具** | `style_rewrite` 等工具供 Agent 调用 | **服务端**（检索、卡库、审计） | 任何 Agent 可编排；权限面可控；上下文最省 | 没有服务端时，它只是给静态 Prompt 套了个昂贵的壳 |

### 1.2 决策

> **四种形态是同一份源的不同编译目标，全都要，但按依赖顺序上线：Prompt Pack（v0，已交付）→ Skill + CLI（v0.1）→ MCP（v0.2）。**

真正需要被钉死的不是"选哪种形态"，而是两条纪律：

1. **源唯一**。风格规则住在 StyleCard，去AI味规则住在 `packs/global/deai.negative.zh.yaml`（唯一事实源），模块流程住在各 Pack。所有形态——prompt 文件、SKILL.md、CLI 内部提示、MCP 工具背后的流水线——都从这些源**编译**出来，禁止在任何一个下游形态上单独手改。
2. **顺序由依赖决定，不由喜好决定**。Skill 的价值前提是 pack 结构进了 git（本次已具备）；MCP 的价值前提是背后有检索、账本、审计服务（v0.2 才有）。跳过前提直接上 MCP，得到的只是"用工具调用的方式发送一段固定文本"，除了损失可读性没有任何收益。

### 1.3 为什么"每个模块结尾手写一个大 Prompt"是退化路径

这是最容易顺手做、也最先烂掉的方案：

- **规则复制 N 份**。去AI味规则要出现在每个写作模块里；手写 N 个大 Prompt 就是把同一套规则复制 N 份，改一条要同步 N 处。openclaw-media 已经实际踩过这个坑：风格链和创作链各维护一份反 AI 腔黑名单，集合漂移，审计定级 P1（CPC-07）。
- **无法表达继承**。"全局规则 → 赛道规则 → 作者规则 → 本次任务覆盖"的叠加关系，在一段散文式 Prompt 里既写不清也查不出冲突。
- **不可验收**。大 Prompt 没有 manifest、没有版本、没有 DoD，"改好了没有"永远靠感觉。

所以本方案把交付单位定义为 **Pack**（带 `pack.yaml` manifest 的目录），Prompt 只是 Pack 的 target 之一。写作模块的收尾动作从"写个 Prompt"变成"收口一个 Pack"——差别在于后者强制回答：输入槽位是什么、输出契约是什么、引用了哪些源、DoD 过了没有。

## 2. 交付层（Delivery Layer）设计

这是对原方案新增的一层，位置在原架构图"Exporter"之后：系统的产出不止 `final.md` 三件套，还包括**把能力本身打包成可分发形态**。

### 2.1 Pack 契约

字段定义见 [`schemas/pack_manifest.schema.yaml`](../schemas/pack_manifest.schema.yaml)。要点：

```text
packs/<name>/
├── pack.yaml                 # manifest: 身份/输入槽位/输出契约/目标形态/编译来源/DoD/评测
├── prompt.<用途>.zh.md       # target=prompt 的即用模板（v0 必须有）
└── examples/                 # 填好槽位的完整示例
```

- `inputs` 槽位定义被三种形态共用：prompt 的 `{{槽位}}`、CLI 的参数、MCP 的 arguments，一处定义三处生效。
- `compiled_from` 记录该 Pack 由哪些源拼装（七组块、风格卡、负面规则卡、领域包），这是防止 Pack 退化成孤儿大 Prompt 的关键字段。
- `dod` 七项全真才能标 `usable`——这份清单就是"写作模块收尾"的验收单。

### 2.2 七组块 = 编译的中间表示

原方案第十五节的七个 Prompt 组块（任务合同 / 内容账本 / 风格卡 / 领域包 / 检索范例 / 操作规则 / 输出合同）在本版中的定位明确为**编译中间表示（IR）**：

```text
源:      StyleCard + deai.negative.zh.yaml + DomainPack + 模块流程
           │  (v0: 人工按模板拼装; v0.1: styleos pack build)
IR:      七组块
           │
目标:    prompt.*.zh.md   SKILL.md   CLI 内部提示+校验器   MCP 工具
```

v0 的四个即用模板就是手工编译的结果，`pack.yaml` 的 `compiled_from` 如实记录了源。v0.1 的 `styleos pack build --target prompt|skill` 把这一步自动化，同时产出**代码校验清单**——负面规则既注入 Prompt 又生成 validator 的双投影，这是从 openclaw-media 学来的已验证模式（`anti_patterns.yaml` 同时进 prompt 和 `validate_version_text` 硬校验）。

### 2.3 写作模块完成的定义（DoD）

任何新写作模块（现在的六个，以后的基金申请书、白皮书、演讲稿……）收尾时逐项打勾：

1. `packs/<name>/` 目录存在，`pack.yaml` 合规；
2. prompt target 可即插即用，槽位与 `inputs` 一致；
3. 模板内嵌自检步骤（账本回归 + 负面规则扫描），不依赖使用者记得检查;
4. 引用负面规则 SSOT，而不是内联一份私有黑名单；
5. `examples/` 至少一个完整示例；
6. 人工盲测对基线（一句话提示）偏好率 >0.6；
7. 复核确认模板不诱导从范例继承事实（形实分离）。

## 3. 各写作模块交付规范总表

| 模块 | Pack | 输入 → 输出 | 状态 |
| --- | --- | --- | --- |
| 去AI味改写（通用兜底） | `global.deai` | AI味稿 + 强度 → 账本/改写稿/修改说明/自检 | **usable** |
| 博主风格蒸馏 | `distill` | 3–10篇语料 → StyleCard(draft) + 证据规则表 + 待确认清单 | **usable** |
| 指定风格创作 | `imitate` | StyleCard + 信息点/原稿 → 提纲/成稿/自检 | **usable** |
| 自媒体口播脚本 | `self_media` | 选题+信息点+人设 → 钩子/口播稿/字幕/发布配套/自检 | **usable** |
| 科研论文 | `academic` | 章节+期刊+学术卡+LaTeX原文 → 改写稿+diff+主张强度核对 | planned → v0.1 |
| 商业计划书 | `business` | 材料类型+陈述定级清单 → 改写稿+定级核对+数字回归 | planned → v0.1 |

蒸馏在本版被升格为**写作模块之一**（原方案把它当纯后台流程）：它同样有即用形态、同样走 Pack 契约——这样"给一个新博主建卡"这件事本身也是即插即用的。

科研与商业两个模块的完整范围沿用原方案第七节；其"规范载体"将参照 openclaw-media `config/platform_mechanisms/*.json` 的结构（`baseline_summary` / `core_signals` / `forbidden_claim_patterns` / `evidence_policy`）分别派生 `academic_norms` 与 `bp_norms`——平台机制契约里的 `forbidden_claim_patterns`（如小红书禁"保证爆款/必爆"）与学术禁"无据首次发现/证明了"、商业禁"行业第一/保证回报"是同构问题，不需要发明新结构。

## 4. 与 openclaw-media 的关系

盘点结论（细节见 [`02_openclaw_media_复用清单.md`](02_openclaw_media_复用清单.md)）：

1. **那边已经有一条完整的去AI味改写链路**（`selfmedia/style/`）：请求契约（含 `must_keep`/`avoid`）、上下文装配、18 条反 AI 腔禁语、代码级子串硬校验、四维评分（naturalness/voice/clarity/fact_fidelity，取最小值聚合）、产物落盘、反馈记录。
2. **那边没有的正是 StyleOS 的增量**：文风特征提取器与 StyleCard 实体不存在；且仓库明令禁止在库内另建风格 SSOT（`FORBIDDEN_STYLE_SSOT_NAMES` 护栏）。

### 定位决策

> **StyleOS 独立成仓（本仓库），作为跨赛道的风格 SSOT 与文风引擎；openclaw-media 是它的第一个宿主。**

理由：openclaw-media 的架构洁癖（唯一代码责任方、禁止第二套风格 SSOT）恰好说明风格资产需要一个明确的家——要么在它库内扩建，要么独立。而 StyleOS 要服务科研论文和商业计划书，这两个赛道与自媒体运营系统无关，塞进 openclaw-media 违反其"唯一职责"原则。独立后的对接方式：

- **规则下沉**：`deai.negative.zh.yaml` 吸收 openclaw-media 的 18 条禁语与创作链的口播规则（已完成，见规则卡），未来作为共享 SSOT 回灌，替代其两份漂移的黑名单（正是审计 CPC-07 开出的修法）。
- **卡片注入**：StyleCard 经 human_approved 后，可渲染进 `style_polish` 的 context（其 `account_profile` 本就承认"缺少语言风格信息"是缺口，约束 30）。
- **能力复用**：v0.1 的 CLI 直接采用那边验证过的形状——`{value, evidence, confidence, reason}` 四元组（creator_profiles）、`LLMValidationContract` 契约注册表、`media_vault` 式产物落盘与租户隔离、`--no-write/--dry-run/--smoke` 三档降级、阶段落盘断点续跑（viral_content runner）。
- **明确不复用**：飞书集成、tag-router、Bot Center 前端、商务/热榜模块。

## 5. 修订后的路线图

### v0 —— 即插即用包（本次交付，零基础设施）

四个 usable Pack + 三个 Schema + 本方案。验收方式：接下来两周在真实任务上用，每次对比"一句话基线"，把手改记录攒下来（它们是 v0.1 蒸馏迭代和未来评测集的原料）。

### v0.1 —— 文风编译器（原方案 v0.1，技术栈按盘点修订）

- `styleos` CLI（uv tool 安装）：`ingest / distill / rewrite / review / feedback / pack build`；
- 确定性统计特征（句长分布、标点频率、n-gram、口癖计数）由代码预计算，喂给蒸馏 Prompt——20 问问卷中约三分之一的维度从"模型估算"变成"代码测量"；
- 程序化内容账本：抽取与回归改为独立节点，锁定项校验不再依赖模型自觉（复用 `validate_version_text` 的子串扫描模式）;
- `academic` 与 `business` 两个 Pack 交付 usable；
- skill target：`pack build --target skill` 生成 `.claude/skills/`，git 同步到所有 Mac 终端；
- profiles/ 卡库：StyleCard 版本管理与人工批准流。
- 技术栈修订：pydantic **v2 原生 API**（那边的 v1 兼容层写法不抄）、**pyyaml**（不抄手写解析器）、契约路径全部参数化（那边的 `/home/ubuntu/...` 仓外绝对路径是明确的坑）；LLM 接入层自建薄封装或改造 `llm_client.py` 增加 Anthropic transport（其现有三种 transport 均非 Claude API）。

### v0.2 —— 服务端与 MCP（原方案 v0.2）

- 腾讯云端：Postgres + Qdrant 混合检索 + COS，Docker Compose；
- MCP 工具上线：`style_distill / style_rewrite / style_search / style_profile_get / style_feedback / style_export`（原方案第十四节清单，底层操作不暴露）；
- 多媒体接入：视频/音频语料进蒸馏。转写二选一——部署在云端且接受阿里云依赖，直接复用 openclaw-media `content_flow` 的 DashScope ASR（含说话人分离）；要求本地化/离线，按原方案上 faster-whisper。**注意那边没有 whisper 集成，原方案此处假设不成立，需自建**；
- Mac 采集器、断网队列、反馈闭环（accept/reject 进 Preference Memory）。

### v0.3 —— 自动优化与高级记忆（原方案 v0.3，不变）

DSPy 提示词优化、LangGraph 人工审批（openclaw-media 的 `content_flow` 已用 LangGraph，有内部先例）、Langfuse、事实层 GraphRAG/HippoRAG、必要时轻量微调。

## 6. 对原方案的其他修订点

1. **负面规则升格为独立 SSOT 文件**（原方案将其作为 StyleCard 的一个字段）。StyleCard 只保留作者特有负面项与对全局规则的覆盖。依据：规则被所有 Pack 共享，放卡内必然复制。
2. **规则双投影成为硬要求**：每条负面规则同时是 Prompt 注入项与（v0.1 起）代码校验项；且关键约束句必须有测试断言其确实出现在构建出的 Prompt 里（openclaw-media 审计发现其"像人"修复全是无测试引用的 prompt 字符串，唯一反例 `test_style_polish.py:143` 反而是正确做法）。
3. **评分维度沿用并扩展**：v0.1 校验器采用那边的 4 维整数评分（naturalness/voice/clarity/fact_fidelity）+ 最小值聚合（保守打分），学术态加 claim_strength_match，商业态加 statement_grading_intact。
4. **蒸馏语料授权红线前置**：写进 distill pack 正文而非只在方案里——未经授权仿写他人并对外署名发布的用法不做。
5. **AI 检测器分数不做目标**：保留原方案立场，写进每个 Pack 的边界说明。
